# Open Paho Java issues: does this client have them?

This checks the open issues of [eclipse-paho/paho.mqtt.java](https://github.com/eclipse-paho/paho.mqtt.java/issues)
against this client, leaving out MQTT v5 issues, as of 1 November 2026. It covers every open issue: the newest 60
(#1101 to #978) in the first part, and the remaining ones (#977 to #22) in
[the second part](#part-2-the-older-issues-977-to-22). [A summary of the fixes](#summary-what-affects-this-client) comes
first.

Each issue is either a **bug** (the client does something wrong), a **feature request** (something Paho doesn't do
and is asked to), or **support / not applicable** (a question, a problem in someone's setup, or something about Paho's
own build, releases, documentation, C library or Android service).

Where an issue could be tested, the test is in `paho-issues/tests`, written so that it **passes once this client
behaves correctly**. A test that fails today shows the client is affected, and can be moved into `src/test/java` with
the fix (as was done for the four fixed below). Run them with:

```sh
paho-issues/run.sh PahoIssueConnectHangTest PahoIssueSessionTest   # simple class names
```

The script compiles the client, its tests and these tests, then runs JUnit. Tests that need a broker start their own
mosquitto: `MosquittoBroker`, as the project's tests do, or `UnlimitedMosquitto`, which has no limit on queued or
in-flight messages. With mosquitto's defaults (1000 queued, 20 in flight), a subscriber that falls behind loses
messages in the broker whatever the client does, so the load tests use the second.

## Not a Paho issue: listeners lost on reconnect

Fixed in `784bdff`. Found while testing #1098. A subscription made with a per-subscription listener, such as
`subscribe(topic, qos, listener)`, loses its listener when the connection drops:

- `MqttChannelHandler.channelInactive` and the channel close listener in `MqttAsyncClient` clear every subscription map.
- With `cleanSession=false` the broker keeps the subscription. After the automatic reconnect it sends the queued
  message and the new ones, the client acknowledges them, and with no listener left (and no client-wide callback set)
  they are lost.
- `PersistentSessionListenerTest` shows this. The listener got the message sent before the drop, but neither the one
  queued during it nor the one sent after the reconnect.

Paho keeps message listeners until `unsubscribe()` or `close()`. With a clean session it doesn't matter: the broker
drops the subscription as well, and the application has to subscribe again.

## Notes on the fixes

**#1101.** Netty's `MqttEncoder` (4.1.137) does not check lengths: it writes the length modulo 65536 and then the
whole string. A 65546-byte topic went out as topic `tttttttttt` with the rest of the topic in the payload, and a QoS 1
publish timed out as the broker read its packet identifier from the topic's bytes. The client now checks topics and
topic filters (publish, subscribe and unsubscribe, single and array forms), the user name, the password and the will
topic and payload, and throws `IllegalArgumentException` for anything over 65535 bytes. Netty's encoder itself still
writes wrapped lengths (`PahoIssue1101LongStringTest` shows it), which could be reported to Netty.

**#1090.** `MessageCatalog` looked up Paho's `ResourceBundleCatalog` class by name, which doesn't exist here, so
`getMessage()` returned `""` for every code. It now returns the description from `MqttExceptionReasons`, which has
one for every code and names unknown codes ("Unknown MQTT error code: 12345"). `toString()` no longer repeats the
message when the cause only restates it, and `MessageCatalog` falls back to the same descriptions.

**#1079.** `isReconnecting()` (on `MqttAsyncClient` and `MqttClient`) is `true` from a connection loss until a
reconnect succeeds, `disconnect()` or `close()` is called, or the retries run out, including while waiting between
attempts, when `isConnecting()` is `false`. `disconnect()` during reconnect already worked. Note that automatic
reconnect
gives up after `setMaxRetries` attempts, 2 by default (Paho retries for ever); `getConnectRetryCount()` then goes back
to 0.

**#1076.** `examples/pom.xml` is a separate project, so the library still doesn't depend on BouncyCastle. It uses the
library from the local Maven repository: `mvn install` the library, then `mvn package` in `examples/` gives
`target/evanino-mqtt-java-examples.jar` with its dependencies in `target/lib`. See UsingSSL.md.
